02 / Mechanism and impact

Requests are cheap.
Waiting has a cost.

In a normal TCP connection, a SYN is followed by a SYN-ACK and a final ACK. A SYN flood can leave many connection attempts waiting for that last step, exhausting the server’s pending-connection capacity. The scenario’s SYN volume and timeouts fit this mechanism; connection-state evidence would strengthen the diagnosis.

The business impact is direct: customers cannot browse promotions, while employees cannot retrieve vacation packages for their clients. Lost bookings are a risk, not a measured financial outcome in the evidence.

03 / Response and manager briefing

Contain first.
Build a durable defense.

In the scenario, the analyst temporarily takes the server offline and blocks the observed source IP at the firewall. Taking the server offline also interrupts legitimate service; it is an emergency action, not an enduring fix. A single IP block is fragile when sources change or are spoofed.

  1. 01Preserve and confirm

    Retain the capture and alert records. Inspect connection states, SYN rates and server resources; establish the affected period and scope.

  2. 02Mitigate with the hosting team

    Evaluate platform-supported SYN cookies or a SYN proxy, connection-rate controls and upstream DoS protection. Tune for legitimate traffic; a firewall or proxy can itself become overloaded.

  3. 03Restore and verify

    Bring the service back under monitoring. Verify new TCP connections, employee access and customer browsing; watch for recurrence and document residual risk.

Brief for the manager

We suspect a TCP SYN flood is disrupting the sales website. Customers and staff are experiencing timeouts. The observed source was blocked and the server was taken offline temporarily. We need hosting-provider support to confirm connection exhaustion, introduce resilient mitigation and validate service recovery.

Section 1: Identify the type of attack that may have caused this 
network interruption
	One potential explanation for the website's connection timeout error message is:
A TCP SYN flood attack, which is a type of Denial-of-Service (DoS) attack that overwhelms a server with connection requests, preventing legitimate users from accessing the website.
The logs show that:
If the TCP logs show a large number of SYN packets being sent to the server without completing the TCP three-way handshake, this suggests that connection requests are overwhelming the server.
This event could be:
A DoS attack intended to disrupt the website's availability. If the malicious traffic originates from multiple systems, it could be a Distributed Denial-of-Service (DDoS) attack.
	

Section 2: Explain how the attack is causing the website to malfunction
	When website visitors try to establish a connection with the web server, a three-way handshake occurs using the TCP protocol. Explain the three steps of the handshake:
1. SYN: The client sends a SYN packet to the server to request a connection.
2. SYN-ACK: The server responds with a SYN-ACK packet to acknowledge the request and indicate that it is ready to establish the connection.
3. ACK: The client sends an ACK packet back to the server, completing the handshake and establishing the TCP connection.
Explain what happens when a malicious actor sends a large number of SYN packets all at once:
The server attempts to respond to each SYN packet and waits for the final ACK to complete the connection. If too many requests remain incomplete, they can fill the server's connection queue and consume resources. This prevents legitimate users from establishing new connections, causing delays or connection timeouts.
Explain what the logs indicate and how that affects the server:
Repeated SYN packets without completed TCP handshakes would suggest a possible SYN flood attack. The large number of incomplete connections can overwhelm the server's capacity to handle new connections, making the website slow or temporarily unavailable to legitimate visitors.
